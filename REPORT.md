# Native ARM64 TinyCC Feasibility Report

## Conclusion

gdcc's pinned TinyCC can compile a complete gdcc-generated C project into a
loadable GDExtension on native **Linux aarch64** and **macOS arm64**. Independent C
API and Java 25 FFM drivers both produce extensions that pass the real Godot
runtime assertions. Coroutine thread isolation, repeated shared-library unload,
and executable HRX thunks also pass after the fixes below.

This establishes feasibility, not production readiness of gdcc's Java backend.
The probes use direct `TCC_OUTPUT_DLL` compilation of all C files in one state.
The current gdcc backend instead compiles each translation unit to an object,
maintains an object cache, and links objects in a fresh state. That pipeline,
bundle installation, and the full script suite are **not validated here**.

Validated source revision: `6046d2594dfb02e41dce28cccf39117f51a2250e`.
Both jobs in [run 38277297631](https://github.com/script-gd/probe-env/actions/runs/38277297631)
completed successfully. The workflow's architecture check excludes x86_64;
these results do not use QEMU or Rosetta.

Godot runs twice per platform, once for each compiler driver. Each run creates
the generated class, exercises integer/string/boolean Variant marshalling and
formatting, checks `value=42`, `value=ARM64`, and `value=true`, then frees the
instance. Its successful tail is:

```text
GDCC_CASE_PASS::value=42
GDCC_CASE_PASS::value=ARM64
GDCC_CASE_PASS::value=true
GDCC_PROJECT_PASS
```

The Linux patched coroutine DSO is additionally checked with `readelf -lW` to
reject any `PT_TLS` segment. The loader has its own nonzero compiler-generated
TLS sentinel and checks it is unchanged after calls. The two worker threads
rendezvous while their coroutines are running, so a process-global replacement
for coroutine TLS would fail rather than accidentally pass sequential tests.

## Required Fixes

### 1. ARM64 ELF assembly syntax

The original minicoro ARM64 directives use `.type _mco_switch #function` and
`.type _mco_wrap_main #function`. TinyCC's assembler rejects this on Linux with
`error: ',' expected (got '#')`.

The ARM64 ELF branch in `fixture/include/gdcc/minicoro.h` now uses:

```asm
.type _mco_switch, %function
.type _mco_wrap_main, %function
```

The unrelated ARM32 branch is unchanged. A successful macOS compile alone would
not reveal this Linux-specific assembler failure.

### 2. DSO-safe coroutine TLS

The pinned ARM64 backend's `__thread` code uses local-exec TLS rather than a
safe dynamic TLS implementation for these loaded images. Its Mach-O path does
not supply correct Darwin TLV behavior either. The negative test demonstrates
that linking is not sufficient: on Linux the DSO's expected-zero variable reads
the host's `0x12345678` sentinel; on macOS it crashes.

For TinyCC on POSIX, minicoro now uses `pthread_once`, `pthread_key_create`,
`pthread_getspecific`, and `pthread_setspecific`. Both coroutine transition
writes and `mco_running()` use this same thread-specific storage. Other compiler
paths retain their existing storage. This is not a global-state fallback and
does not require changing TinyCC's compiler TLS implementation.

The image destructor deletes the key. The declaration deliberately uses
`__attribute((destructor))`, not `__attribute__((destructor))`: on the tested
glibc headers, TCC's lack of `__GNUC__` allows the latter spelling to be
macro-erased. The initial destructor attempt leaked keys and exhausted them
during repeated loads; the corrected declaration passes 1100 unload rounds on
both platforms.

The host must stop calls and drain coroutines before unloading their image.
Deleting a key is not a solution for concurrent execution in unloaded code.
The experimental helpers `abort()` on pthread initialization/storage errors;
a production error-reporting policy remains to be decided.

### 3. macOS libtcc symbol isolation

The pinned TinyCC Makefile builds `libtcc.dylib` with `-flat_namespace`. The C
driver successfully compiles the fixture with that library, but the Java FFM
driver crashes on its first translation unit inside `preprocess_start+0x53c`.

The latest artifact establishes a concrete symbol collision, not just a theory:

```text
dyld[1639]: <libtcc.dylib/bind#31> -> 0x1a4cf5544 (Heimdal/_parse_flags)
```

TinyCC declares `ST_DATA int parse_flags` in `tccpp.c`. The JVM crash report
identifies register `x9` as `parse_flags+0` in Apple's Heimdal framework, with
fault address `0x1a4cf5544`. The faulting instruction is a store through `x9`.
Flat namespace has bound a TinyCC data reference to an unrelated function.

`scripts/probe.sh` first requires the failing flat-namespace result, then
rebuilds the same sources with:

```bash
make -C build/tcc -B -j2 LDFLAGS=-Wl,-twolevel_namespace tcc libtcc.dylib
```

`otool -hv` confirms the rebuilt dylib has `TWOLEVEL` (the original does not).
The same FFM driver then compiles all five units and the output passes Godot.
The build override changes the host libtcc link flags, not the TinyCC-generated
extension compiler source. Production bundle builds must preserve this
isolation; a C-only smoke test would miss the failure.

### 4. macOS ARM64 instruction-cache API

Calling the pinned TinyCC `__arm64_clear_cache` implementation directly raises
an illegal instruction on the macOS runner. The raw builtin probe must fail
before the patched HRX test is accepted.

`fixture/include/gdcc/gdcc_hrx.c` now uses Apple's
`sys_icache_invalidate(addr, size)` from `<libkern/OSCacheControl.h>` on Apple
ARM64. Linux TinyCC retains `__arm64_clear_cache`. This keeps cache maintenance
behind the platform API rather than depending on unprivileged access to ARM
cache-control registers that may not be available on Darwin.

The HRX probe executes the ARM64 machine-code thunks, asserts that the anchor
does not retain image-local free/reference callbacks, invalidates the old
generation, checks identity rebinding and fail-closed missing identities, and
reclaims specs. It checks that shared thunk addresses and bytes remain unchanged
across simulated generations.

## Integrating Into gdcc

The original Java backend still refuses these platforms. The independent FFM
probe does not bypass this guard in gdcc or install an ARM64 bundle there.
At the inspected source reference, integration requires:

1. Add `LINUX_AARCH64` and `MACOS_AARCH64` to `TinyCcCompiler.SUPPORTED_PLATFORMS`.
   `TargetPlatform` already has both enum cases and native architecture parsing.
2. Add bundle keys, platform mapping, and required-layout checks in
   `TinyCcBundle`; currently only `linux-x86_64` and `windows-x86_64` are mapped.
3. Make `TinyCcBundle.libraryPath` select `bin/libtcc.dylib` for macOS instead of
   treating every non-Windows target as `bin/libtcc.so`.
4. Add native bundle build scripts and CI jobs for the new keys, including the
   macOS two-level namespace link flags and the helper fixes above.
5. Preserve the `VERSION`, pinned commit, format-version, licenses, and hashed
   `MANIFEST` checks. On the tested non-PE targets, `libtcc1.a` belongs at the
   `{B}` bundle root, not Windows' `{B}/lib` layout.
6. Wire bundles into the shipped classpath under `gdcc/tinycc-bundle/<key>/`, or
   explicitly distribute a bundle directory via `GDCC_TINYCC_HOME`. The inspected
   jar/resource configuration does not currently package those bundle resources.
7. Update test bundle discovery and native-library filename checks, and run the
   real `TinyCcCompiler` FFM tests on both new hosts. Validate fresh object builds,
   cache hits, cache rejection/rebuild, diagnostics, and final Godot execution.
8. Validate the macOS intermediate-object path specifically:
   `tcc_set_output_type(TCC_OUTPUT_OBJ)` forces ELF, and `tcc_output_file` returns
   through `elf_output_obj` before reaching `macho_output_file`. Final
   `TCC_OUTPUT_DLL` uses the Mach-O writer. No probe compiles or relinks an
   intermediate object, so gdcc's object cache and fresh-state relinking remain
   untested on this path.
9. Discover or allow overriding the macOS SDK at runtime. Configure embedded an
   absolute Xcode SDK include directory on this runner; shipping that path as-is
   would not make a portable bundle. Define deployment/signing policy separately.

`TinyCcLibrary` uses the platform's native FFM linker and its pointer/int API is
not intrinsically x86_64-only. Nevertheless, the full production binding,
locking, cancellation, callback-failure paths, and bundle lifecycle need their
own end-to-end tests. Removing only the supported-platform guard is insufficient.

## Validation Boundaries

- One complete generated script project was tested, not the entire gdcc suite.
- Coroutine behavior is tested directly through minicoro, not a generated
  GDScript `await` program; migration of a coroutine between threads is untested.
- HRX generation changes use gdcc's fake-engine probe in one executable, not a
  real Godot editor reload that unloads one DSO and loads a different generation.
- The 1100-round unload test exercises the coroutine DSO and TLS key cleanup;
  it does not certify every gdcc/Godot hot-reload lifetime path.
- FFM registers a diagnostic upcall but no deliberate invalid-C input was used
  to exercise its error path. Production object-cache compilation is untested.
- Successful RW-to-RX thunk publication on the runner does not cover every
  hardened-runtime, entitlement, sandbox, or signing configuration. Keep HRX
  failure paths fail-closed.
- Results cover Ubuntu 24.04/glibc and the observed macOS/Xcode environment,
  not musl, Android, older glibc, or all SDK/deployment targets.
- IntelliJ MCP build/inspection requests returned output-schema errors in this
  environment; they are not recorded as build successes. Actual native CI
  compilation and runtime assertions supply the validation evidence.
